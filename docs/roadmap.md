# Roadmap and known limits

## Next

- Done in 0.9.0: **people in photos.** Faces are found by OndolSaem 0.3.0 (ML Kit detection + SFace, category `face`) during indexing and grouped by person on the phone (on by default; off deletes all face data, on again scans faces only). New People menu (names, merging, "not this person", cover face) and `person` for the chat's `search_index`, `move_files` and `delete_files`. Limits: photos only (not video frames), side views, masks and small faces are often missed or form their own groups, children's faces change over the years, names are lost when face grouping is turned off or the face model changes.
- Done in 0.8.1: the low-power indexing switch is gone (it chose the CPU backend, which OndolSaem now decides).
- Done in 0.8.0 (checked on the emulator: upgrading an indexed 0.7.1 install deletes its models and keeps the index without re-indexing): **models moved to the companion app OndolSaem / 온돌샘** (separate repository `taehunkim/ondolsaem`). Nunsori no longer downloads or runs models and has no network permission; `ml/ModelHost` reaches OndolSaem's bound service through its client SDK, with leases that keep a model loaded during an indexing pass or a chat turn, background priority for indexing, chat tools called back into Nunsori, and the host's active model ids mirrored into the settings so a model change there re-indexes what it affects (callback while connected, broadcast otherwise, check on every refresh). Models downloaded by earlier versions are deleted on upgrade (download them again in OndolSaem); model ids are unchanged, so the index stays valid. Settings › Models and the first-run wizard show the connection to OndolSaem instead of model cards.
- Done in 0.7.0: the app is now **Nunsori / 눈소리** with its own launcher icon (adaptive, themed) and a new `applicationId` (`io.github.taehunkim.nunsori`). It installs as a separate app from 0.6.x, so models and the index are set up again; the code package stays `com.lsa.app`.
- Done in 0.6.1: chat usability: composer follows the keyboard without a gap, copy/share of messages as Markdown, thumbnails of mentioned files under answers (tap opens the file), own status-bar icons for indexing and task notifications; Settings is split into tabs; a tools checklist menu replaces the chips (and adds the missing move/delete switch); keyboard no longer pans the whole screen (`adjustResize`).
- Done in 0.6.0: action cards for the chat: calendar-event and contact proposals (system app opens prefilled) and file move / trash / delete (approval first, trash by default, needs All files access). Scheduled runs can propose actions too (cards wait in the chat, the notification counts them). Later ideas: restoring from `.LSA_Trash` in the app, opt-in auto-approval per task.
- Done in 0.5.0: scheduled chat tasks (time-based with exact alarms, and after-indexing file triggers), confirmation cards, notifications that open the chat, background-access checks (notifications, exact alarms, battery optimization).
- Done in 0.4.0: failed-file list and retry, embedding-length guard, pinned chats, Markdown, chat instructions, low-power indexing, folder presets, resource indicator.

### Planned, in priority order

1. **Model host follow-ups (OndolSaem, done in 0.8.0).** Open points (real-device numbers, two apps indexing at once, more models, an audio-capable default embedding model, first-run screens) are tracked in OndolSaem's `docs/roadmap.md`. Done in OndolSaem 0.2.0: the SDK builds on JitPack from the tag `sdk-v0.2.0` (JDK 21) and Nunsori uses it; background requests of several apps take turns; third-party apps ask for the user's approval in OndolSaem, and Nunsori shows *Allow in OndolSaem* when it is signed with an unknown key; when Android refuses the keep-alive service in the background, OndolSaem notifies and offers to turn off battery optimization. The low-power indexing switch was removed in 0.8.1 (OndolSaem picks the backend).
2. **Companion AI note-taking app on the same model host, searchable from Nunsori.** A separate notes app built on OndolSaem (item 1) (its own AI features such as summaries, dictation with SenseVoice and tidying notes use the shared models), whose notes Nunsori indexes and finds next to photos and documents; tapping a note result opens it in the notes app. Sketch: the notes app exposes its notes through a `ContentProvider` (`id`, `title`, `body`, `updated_at`, `deep_link`) guarded by a `signature`-level permission; Nunsori adds an external-source kind in `data/media` that `IndexRunner.sync()` walks, re-embeds only notes whose `updated_at` changed and drops notes that disappeared; change detection through a `ContentObserver` or a broadcast from the notes app that wakes the automatic indexing; the result card opens `Intent(ACTION_VIEW, deep_link)` (disabled when the notes app is not installed), and the chat tools (`read_file` or a sibling) read the note body from the provider. Nunsori keeps one central index (it embeds the notes itself) instead of federated search, so notes rank together with everything else on one scale. Needs a schema change (`items` is file-path based today: source kind, external id and deep link columns, with a DB version bump and a Migration). Documenting the provider columns as a **Nunsori source contract** lets other apps that follow it plug in too, which is the cleanest route for item 3. Builds on OndolSaem (item 1) for its own AI features; the provider link itself does not depend on it.
3. **Direct integration with other apps' content for search.** Index more than files: text messages (SMS/MMS), notes and similar sources, so one search and the chat cover them. Needs per-source feasibility work: SMS/MMS means the sensitive `READ_SMS` permission and a content provider reader (fine for a sideloaded app, restricted on Google Play); notes apps mostly have no public provider (Samsung Notes, Google Keep), so the realistic routes are exports or shared text into the app, notification capture, or plain-file notes (Markdown/text folders are already indexed). Each source also needs its own opt-in, a source-aware result card (open the message or note in its app) and a privacy review.
4. **Web tools for chat (lowest priority).** Web search and fetching a page for the chat model. They go against the app's on-device principle (queries and page requests would leave the phone), so they are pushed behind the work above. If built: an opt-in setting that is off by default, a clear disclosure of what leaves the device, and a search API choice; the app only uses the network to download models today.

### Other ideas

- **Show the face model in the OndolSaem card:** Settings › Models and the first-run wizard list the models Nunsori uses from OndolSaem (`USED` in `ui/settings/HostSection.kt`: search, text in images, speech, chat) but not the face model added in 0.9.0, although face grouping uses it (`ModelHost.faces()`). Add a *Faces* row (`Categories.FACE`, with en/ko strings) that shows the model, "not downloaded", or "needs OndolSaem 0.3.0" on an API 1 host, so the user sees why People stays empty.
- **Sub-agent for images:** the chat model cannot look at an image that a tool returns (tool results are text only), so a search hit that is a photo stays a file name and OCR text. Idea: a tool such as `describe_image(item_id, question?)` that starts a separate, short model call (a sub-agent with its own small prompt and no tools) that does see the image, and hands back a summary or description (optionally answering a specific question about it) as the tool result. The same pattern could serve other jobs that would clutter the main context (summarize a long document, check one file against a condition). Open points: which model does it (the chat model when it has vision, otherwise a vision-capable one) and the memory cost of loading it next to the embedder (see `ml/ModelResidency`), latency on a phone (one call per image, so a cap per turn), caching descriptions per file so they are not recomputed (possibly reusing them as search text, which touches the indexing pipeline and `PipelineKeys`), a prompt that keeps descriptions short for the 4K window, and whether scheduled runs may use it (battery).
- **Agent skills for the chat:** reusable instruction bundles (a name, a one-line description and a Markdown body, in the spirit of agent skills) that the user can add, edit and switch on per chat or for scheduled tasks. Sketch: the system prompt lists only each active skill's name and description; a small tool (for example `use_skill`) returns the full body when the model decides it applies, so the context cost stays low on the 4K default window. Open points: where skills live (app storage, imported from a folder or a shared file), a few built-in examples (receipt summary, weekly digest), how a skill may refer to the existing tools, whether scheduled runs can use them, and a size limit per skill. Skills stay plain text; they never run code.
- **More reliable tool calls with the small chat model:** seen on the emulator with Gemma 4 E2B: for "When a photo of a business card is added, add the person to my contacts" the model called `schedule_task` without the required `trigger` argument, got `Error: trigger must be time or file.` and still told the user "I have scheduled a task … please confirm", although no task card existed (a second try with "Schedule a file task: …" worked). Ideas: infer a missing `trigger` (a `query`/`kinds` argument means a file task, a time argument means a time task) in `TaskManager.propose`; return a more actionable error that lists the arguments and an example call; let `ChatController` retry once when a tool returns an error before the model may answer, or show the failed call as an error card so the user is not told something succeeded; add a test with the failing argument shapes. Check the same for the other write tools (`add_contact`, `add_calendar_event`, `move_files`).
- **File-type filter of file-triggered tasks seems not to hold (to investigate and fix):** with a request such as "only photos of …" the task appears to fire for every new file, not just the named kind. In the emulator test the confirmation card read "When a new  file matching …" with an empty kind, so the model may not pass `kinds` at all (it is optional in the `schedule_task` schema, see `ScheduleTools`), or the filter in `TaskManager.onIndexed` / `fileTask` may not be applied to the candidates. To check: what `kinds` the model sends for "photo", "document" and similar words, what `fileKinds` is stored, and whether `onIndexed` filters by it before the match and the *Let the assistant judge new files* path (which queues every new file with text when there are few). Ideas: show the kinds on the card ("new image matching …"); infer `kinds` from words in the instruction when the model leaves it out (photo, picture, image, PDF, document, recording, video); a test per kind that checks a non-matching file never becomes a candidate.
- **Export / import the index inside the app:** copy the index database and thumbnails to a file (or restore them from one) so that reinstalling, moving to a new phone or switching between debug and release builds does not force a full re-index. Today `adb run-as` can copy the data between debug builds only, and not at all into a release build (not debuggable; `allowBackup` is off). Open points: file format and DB version check (Room migrations already cover older versions), what to include (models are large and re-downloadable, so leave them out), where the file goes (SAF picker), and privacy (the file holds the extracted text of the user's files).
- Chat: attach arbitrary files that are not indexed (text extraction on the spot), NPU/GPU choice, summaries for long chats instead of dropping old messages.
- Additional models: MobileCLIP2-S0 (listed, not implemented), PP-OCRv5.
- Real-device performance measurements (GPU/NPU paths, thermal behaviour).
- Multiple embedding models at the same time.
- Embed place names as text segments (`PLACE_TEXT`) for fuzzy place queries; skipped for now because name matching plus aliases covers the common cases.
- Geotags for videos.

## Possible scaling work

- FTS5 trigram index if `LIKE` keyword search gets slow.
- 256-d vectors and/or an ANN index beyond about 300k segments.

## Known limits

- Office files are not rendered: text plus a generated text card only. Old .doc/.ppt/.xls and hwp are unsupported.
- Vectors are scanned in memory (int8); target about 300k segments.
- Video is embedded per scene/length clip, so moments shorter than a few seconds can be missed; precision is configurable.
- Only the 740M model embeds audio; input is limited to about 40 s per clip.
- Emulator inference is CPU only and slow.
- The small default chat model sometimes calls a tool with missing arguments (for example `schedule_task` without `trigger`) and then claims success; the user should check that a task card appears (see the idea above).

- Automatic indexing is a WorkManager job: the system may delay it (Doze, standby buckets, Samsung *Sleeping apps*) unless the app is excluded from battery optimization; Immediate mode has an hourly safety net.
- Scheduled tasks run one at a time and need the chat model, so a run can be late when another answer is being generated or the phone is in Doze/an OEM sleep list (Samsung *Sleeping apps*); file-triggered tasks run after indexing, never at file creation; a new file counts only if it clearly stands out from the typical similarity of the index (or contains all the query words) and the chat model confirms it; photos without text are not checked by the model (they need their own match), and the similarity thresholds still need tuning with real files. Only files indexed after confirming count. The file-kind filter ("only photos") does not seem to hold yet: tasks may trigger for every new file (see the idea above).
