# Roadmap and known limits

## Next

- Done in 0.11.0: **face grouping threshold in the app.** *Grouping: looser or stricter* (People screen and Settings › Index) sets the similarity two faces need to count as one person (0.30 to 0.60), previews the number of groups and groups all faces again from the stored vectors (no scan), keeping names (to the group with most of their faces), covers and "not this person"; two named groups never mix. The default rose from 0.363 to 0.45 (leaning strict), so the first start of 0.11.0 groups existing faces again once (`faceGroupingKey`).
- Done in 0.10.0: **the chat moved to the companion app Malbotdari / 말벗다리** (separate repository `TaeHunKim/malbotdari`). Nunsori serves its index to other apps (`:sdk` module, `INunsori`: search, read, move/delete prepared for the user's confirmation in the calling app and then committed, thumbnails, new files with a cursor, people's names) and sends an "index changed" hint after a pass; apps signed with Nunsori's key connect directly, others need approval in Settings › App › Connected apps. The chat code, its tables (dropped in schema v9), alarms, task notifications and the exact-alarm and boot permissions are gone; upgrading deletes the stored chats (not carried over). The Chat menu entry and *Ask in chat* open Malbotdari. Chat ideas and limits are in Malbotdari's roadmap.
- Done in 0.9.0: **people in photos.** Faces are found by OndolSaem 0.3.0 (ML Kit detection + SFace, category `face`) during indexing and grouped by person on the phone (on by default; off deletes all face data, on again scans faces only). New People menu (names, merging, "not this person", cover face) and `person` for the chat's `search_index`, `move_files` and `delete_files` (served to Malbotdari since 0.10.0). Limits: photos only (not video frames), side views, masks and small faces are often missed or form their own groups, children's faces change over the years, names are lost when face grouping is turned off or the face model changes.
- Done in 0.8.1: the low-power indexing switch is gone (it chose the CPU backend, which OndolSaem now decides).
- Done in 0.8.0 (checked on the emulator: upgrading an indexed 0.7.1 install deletes its models and keeps the index without re-indexing): **models moved to the companion app OndolSaem / 온돌샘** (separate repository `taehunkim/ondolsaem`). Nunsori no longer downloads or runs models and has no network permission; `ml/ModelHost` reaches OndolSaem's bound service through its client SDK, with leases that keep a model loaded during an indexing pass or a chat turn, background priority for indexing, chat tools called back into Nunsori, and the host's active model ids mirrored into the settings so a model change there re-indexes what it affects (callback while connected, broadcast otherwise, check on every refresh). Models downloaded by earlier versions are deleted on upgrade (download them again in OndolSaem); model ids are unchanged, so the index stays valid. Settings › Models and the first-run wizard show the connection to OndolSaem instead of model cards.

### Planned, in priority order

1. **Better face grouping (algorithm or model).** Face grouping (0.9.0) works, but on real photo libraries many groups mix different people. The emulator fixtures (five public figures, mostly frontal portraits) separated cleanly (same person 0.54 to 0.90, different people at most 0.22), so the threshold was never tested on everyday photos: small, blurry, side or tilted faces, glasses, children, and many similar-looking people (East Asian faces may be under-represented in SFace's training data, which would push unrelated faces closer together). To do, in order:
   - **Measure first:** a labeled set of everyday photos (the user's own, never committed) and a small script that reports how many groups are mixed and how many people are split, for a given threshold and grouping method.
   - **Grouping:** the current method compares a face with each group's mean and merges groups by their means, which lets a group "drift" and swallow nearby people. Try a higher threshold (0.45 to 0.55), matching against the closest few members instead of the mean, merging only when most member pairs agree (average or complete linkage), and leaving low-quality faces (small, blurry, turned: `faces.score`, box size) ungrouped instead of joining a group.
   - **Model:** compare face recognition models that run on a phone and whose weights allow this use (license checked per file; InsightFace's popular weights are non-commercial and stay out), on the same set; it would be a new model in OndolSaem's `face` category (a model change re-scans faces).
   - **User feedback:** "not this person" already blocks one group; it could also teach a per-person threshold, or ask "is this the same person?" for faces near the threshold.
   - **Redo the grouping when its rules change.** Done in 0.11.0 for the threshold and the grouping method (`FaceClusterer.GROUPING_VERSION`, regroup from the stored vectors keeping names, covers and blocks); still open for a new face model (names are lost). Like the search index, face data must be rebuilt when what produced it changes, but at two levels. A new face model (or detection and alignment changes, `FaceIndexer.FACE_KEY_VERSION`) already deletes all faces and scans every photo again (`items.faceKey`), but loses the names. A change of the threshold or the grouping method needs no re-scan: the stored vectors are enough, so regroup all faces from scratch (seconds even for many photos) with a grouping version stored in the settings, the way `pipelineKey` works for the index. In both cases carry the user's work over: give a new group the name of the old named group it shares most faces with (for a new model: the same photos and box positions), keep "not this person" as a rule between faces, and ask when a name would land on two groups.
   - **Threshold in the app.** Done in 0.11.0 (default 0.45, not yet measured on a labeled set). Original idea: a setting such as *Grouping: stricter / looser* (a slider over a safe range, e.g. 0.30 to 0.60) that regroups from the stored vectors at once and shows how many groups it makes before applying. Stricter splits one person into several groups (fixable with *Merge*), looser mixes people (fixable only face by face), so the default should lean strict.
2. **Model host follow-ups (OndolSaem, done in 0.8.0).** Open points (real-device numbers, two apps indexing at once, more models, an audio-capable default embedding model, first-run screens) are tracked in OndolSaem's `docs/roadmap.md`. Done in OndolSaem 0.2.0: the SDK builds on JitPack from the tag `sdk-v0.2.0` (JDK 21) and Nunsori uses it; background requests of several apps take turns; third-party apps ask for the user's approval in OndolSaem, and Nunsori shows *Allow in OndolSaem* when it is signed with an unknown key; when Android refuses the keep-alive service in the background, OndolSaem notifies and offers to turn off battery optimization. The low-power indexing switch was removed in 0.8.1 (OndolSaem picks the backend).
3. **Companion AI note-taking app on the same model host, searchable from Nunsori.** A separate notes app built on OndolSaem (item 2) (its own AI features such as summaries, dictation with SenseVoice and tidying notes use the shared models), whose notes Nunsori indexes and finds next to photos and documents; tapping a note result opens it in the notes app. Sketch: the notes app exposes its notes through a `ContentProvider` (`id`, `title`, `body`, `updated_at`, `deep_link`) guarded by a `signature`-level permission; Nunsori adds an external-source kind in `data/media` that `IndexRunner.sync()` walks, re-embeds only notes whose `updated_at` changed and drops notes that disappeared; change detection through a `ContentObserver` or a broadcast from the notes app that wakes the automatic indexing; the result card opens `Intent(ACTION_VIEW, deep_link)` (disabled when the notes app is not installed), and Malbotdari's tools (through `read_file` or a sibling) read the note body. Nunsori keeps one central index (it embeds the notes itself) instead of federated search, so notes rank together with everything else on one scale. Needs a schema change (`items` is file-path based today: source kind, external id and deep link columns, with a DB version bump and a Migration). Documenting the provider columns as a **Nunsori source contract** lets other apps that follow it plug in too, which is the cleanest route for item 4. Builds on OndolSaem (item 2) for its own AI features; the provider link itself does not depend on it.
4. **Direct integration with other apps' content for search.** Index more than files: text messages (SMS/MMS), notes and similar sources, so one search and the chat (Malbotdari) cover them. Needs per-source feasibility work: SMS/MMS means the sensitive `READ_SMS` permission and a content provider reader (fine for a sideloaded app, restricted on Google Play); notes apps mostly have no public provider (Samsung Notes, Google Keep), so the realistic routes are exports or shared text into the app, notification capture, or plain-file notes (Markdown/text folders are already indexed). Each source also needs its own opt-in, a source-aware result card (open the message or note in its app) and a privacy review.

### Other ideas

- **Export / import the index inside the app:** copy the index database and thumbnails to a file (or restore them from one) so that reinstalling, moving to a new phone or switching between debug and release builds does not force a full re-index. Today `adb run-as` can copy the data between debug builds only, and not at all into a release build (not debuggable; `allowBackup` is off). Open points: file format and DB version check (Room migrations already cover older versions), what to include (models are large and re-downloadable, so leave them out), where the file goes (SAF picker), and privacy (the file holds the extracted text of the user's files).
- Additional models: MobileCLIP2-S0 (listed, not implemented), PP-OCRv5.
- Real-device performance measurements (GPU/NPU paths, thermal behaviour).
- Multiple embedding models at the same time.
- Embed place names as text segments (`PLACE_TEXT`) for fuzzy place queries; skipped for now because name matching plus aliases covers the common cases.
- Geotags for videos.

## Possible scaling work

- FTS5 trigram index if `LIKE` keyword search gets slow.
- 256-d vectors and/or an ANN index beyond about 300k segments.

## Known limits

- Office files are not rendered: text plus a generated text card only. Old .doc/.ppt/.xls and hwp are unsupported.
- Vectors are scanned in memory (int8); target about 300k segments.
- Video is embedded per scene/length clip, so moments shorter than a few seconds can be missed; precision is configurable.
- Only the 740M model embeds audio; input is limited to about 40 s per clip.
- Emulator inference is CPU only and slow.

- Automatic indexing is a WorkManager job: the system may delay it (Doze, standby buckets, Samsung *Sleeping apps*) unless the app is excluded from battery optimization; Immediate mode has an hourly safety net.
